# T21 — `tickets.export` markdown snapshot Implementation Plan

> **For the implementer:** Use `subagent-driven-development` to implement task-by-task. TDD throughout (design spec §16: every Acceptance bullet maps to a named test).
>
> **Stub-first TDD (applies to Tasks 1, 2, 3a):** before writing a test that imports a not-yet-created module, create the module as a typed **stub** that returns an empty/placeholder value. *Because* a test importing a missing module fails with `ERR_MODULE_NOT_FOUND` (an ERROR), not an `AssertionError` (a FAIL) — that is not a valid red step. Stub first → tests go red on assertions → implement → green.

**Goal:** Add a `tickets.export` MCP tool that renders the active project's tickets to a drift-labelled markdown file (default `<root>/.ai/TICKETS.md`), stamped with a loud generated-at banner, and returns a compact result.
**Architecture:** A pure renderer (`src/lib/export-markdown.ts`) turns assembled ticket records + an export timestamp into a deterministic markdown string; a thin tool (`src/tools/export.ts`) resolves the project, collects tickets/tags/relations from the DB, renders, writes the file, and returns `{ path, bytes, ticket_count, exported_at }`.
**Tech Stack:** TypeScript ESM, better-sqlite3, `node:fs`/`node:path`, vitest.

## Ticket-scoped context

Facts specific to *this* ticket (generic invariants are in the cache — not repeated here):

- **`root_path` is already available.** `requireProject(db, { project }, getClientRoots)` returns `ProjectRow = { id, root_path }` (`src/lib/projects.ts:31-34,84-138`). `root_path` is the project's filesystem root, so the default output path is `path.join(project.root_path, ".ai/TICKETS.md")` — **no new resolution code is needed.** This is the single biggest de-risking fact for the ticket.
- **File-writing is a NEW capability for this server.** Every existing tool only touches the DB. `tickets.export` is the first tool to write the filesystem. Use `node:fs` `mkdirSync(dir, { recursive: true })` + `writeFileSync(path, body, "utf-8")`. Keep it boring and synchronous (consistent with better-sqlite3's sync style).
- **Single-project only.** Export resolves one project — do **not** pass `allowAll: true`. `requireProject` without `allowAll` already rejects `project: "all"`, which is the behaviour we want.
- **Export is read-only on the DB.** It mutates no tickets, so it writes **no** `audit_log` row. (Contrast every write tool, which audits.)
- **Tickets schema** (`src/migrations/001_init.sql`, confirmed via `get.ts`): `id, project_id, title, description, status, priority, type, effort, epic, parent_id, created_by, created_at, closed_at`; `tags(project_id, ticket_id, tag)`; `relations(project_id, from_id, to_id, kind, note)` with `kind ∈ {blocks, follows_up, supersedes, relates_to}`.
- **Fidelity reality (from the ticket):** the export renders only DB fields + `description` verbatim. It will **not** reconstruct this repo's hand-authored Scope/Acceptance/Notes prose unless that prose lives in `description`. A regenerated file is leaner than the current hand-maintained `.ai/TICKETS.md`. This is expected and is the whole reason for the banner.
- **`nowIso()`** (`src/lib/now.ts`) returns UTC ISO-8601 — use it for the banner timestamp (inject it into the tool, pass it *into* the pure renderer as an argument so the renderer stays testable/deterministic).
- **Spec reversal is in-scope.** T21 consciously reverses the spec's "no markdown export / TICKETS.md not regenerated" non-goal. The spec amendment is an Acceptance bullet (Task 4), not optional.

## Task 1: Pure markdown renderer + tests

**Files:**
- Create: `src/lib/export-markdown.ts`
- Create: `src/lib/export-markdown.test.ts`

**Decisions:**
- **Pure function, timestamp injected.** Signature `renderExportMarkdown(input: ExportRenderInput): string` where input carries `{ projectId, exportedAt, tickets, statusCounts }` and each ticket record carries its tags + grouped relations already assembled. *Because* purity makes the determinism + banner + field-rendering acceptance bullets unit-testable with zero DB/fs, and injecting `exportedAt` (not calling `nowIso()` inside) is what lets the determinism test assert "only the timestamp line changes".
- **Banner (mandatory, top of file), exactly two parts:**
  1. An HTML comment first line: `<!-- GENERATED BY ticketgraph — DO NOT EDIT BY HAND. Source of truth is the ticketgraph DB. -->`
  2. A visible blockquote: `> **Exported <exportedAt>** from the ticketgraph DB (project \`<projectId>\`, <N> tickets). The DB is the source of truth; this file is a point-in-time snapshot and *will* drift. Re-run \`tickets.export\` to refresh.`
  `<exportedAt>` is the injected ISO-8601 UTC string verbatim.
- **Grouping = by priority, matching the existing file shape.** Sections `## P0`, `## P1`, `## P2`, `## P3`, then `## (no priority)` for `priority IS NULL`, then — if any exist — `## (other: <value>)` sections for **unknown** priority values. *Because* `priority` is free-form `TEXT` with **no CHECK constraint** (`001_init.sql:16`) — values outside `{P0,P1,P2,P3}` are reachable via `tickets.add`/`import_json` (e.g. a stray `"P4"` or `"critical"`). The renderer must **bucket by an explicit priority rank, not a raw string sort**, and never silently drop a ticket whose priority isn't a known P-level. `epic` is rendered as a per-ticket field, not a grouping level (keeps grouping one-dimensional and deterministic).
- **Deterministic ordering:** sections in rank order `P0=0, P1=1, P2=2, P3=3, null=4, unknown=5` (unknown values among themselves ordered by the value string); within each group order by `id` ascending (string sort, matching `list.ts:180`). *Because* an explicit rank handles the unconstrained-`TEXT` reality that a bare `ORDER BY priority` does not; determinism is what the acceptance bullet needs. (Numeric-aware id sort — `T10` vs `T2` — is explicitly out of scope; string sort, consistent with `list.ts`. Note as future polish, do not implement.)
- **Per-ticket rendering:** `### <id> — <title>` heading, then a compact field line (Status, Type, Effort, Epic, Tags — omit fields that are null/empty), a Blockers/Relations block when relations exist, then the `description` reproduced **verbatim** under it. Relations: render incoming `blocks` as `**Blockers:** <from_id>, …`; render other relation kinds (`follows_up`, `supersedes`, `relates_to`, outgoing `blocks`) under a `**Relations:**` block as `<kind>: <id> (note)`.
- **Status table:** after the banner, a `## Status` table with Done / In progress / Open columns built from `statusCounts` (done = `done`+`deferred`; in progress = `in_progress`; open = `open`+`blocked`) — or simpler, a counts line. Keep it to counts, not an exhaustive id list (ids live in the body). *Decision:* render a one-line counts summary `**N tickets** — open: X, in_progress: Y, blocked: Z, done: D, deferred: F` rather than reproducing the hand-file's id-listing table (which drifts and is redundant with the body).

**Don't:**
- Don't call `nowIso()` / `new Date()` inside the renderer, and don't give `exportedAt` a default — it is a **required** argument. (A default re-introduces a second time source and flakes the determinism test.)
- Don't HTML-escape or reflow `description` — reproduce it verbatim (it's already markdown authored by the user/migration).
- Don't invent fields not in the record — render only what's passed in.
- Don't drop a ticket whose `priority` isn't one of `P0..P3`/null — route it to the `(other: …)` bucket.

**Implement:** A pure function that emits banner → counts summary → priority-grouped sections → per-ticket blocks, omitting empty fields, deterministic ordering, description verbatim.

**Verify:** `npm test src/lib/export-markdown.test.ts`. Named tests, one per acceptance facet:
- `it("opens with the DO-NOT-EDIT comment then a timestamped banner naming project and count")`
- `it("renders every ticket grouped by priority with P0..P3 then no-priority")`
- `it("renders status, type, effort, epic, tags and omits empty fields")`
- `it("reproduces description verbatim")`
- `it("renders incoming blocks as a Blockers line and other kinds under Relations")`
- `it("buckets an unknown priority value into an (other: …) section, never drops it")` — fixture with `priority: "P4"` and `priority: "critical"`.
- `it("is deterministic: same input minus exportedAt yields identical body")` — call twice with two different `exportedAt`, assert the two outputs differ only on the banner blockquote line.

## Task 2: DB collection helper + tests

**Files:**
- Create: `src/lib/export-collect.ts` (or co-locate as an exported `collectProjectExport` in `export-markdown.ts`'s sibling — keep collection separate from rendering)
- Create: `src/lib/export-collect.test.ts`

**Decisions:**
- `collectProjectExport(db, projectId)` returns the rendered-input records (sans `exportedAt`): all tickets for the project (every status, no limit), each with its `tags[]` and grouped `relations`, plus the `statusCounts` map. *Because* the renderer must be fed fully-assembled records; this is the only DB-touching part.
- **Bulk queries, not per-ticket loops.** One tickets query, one `SELECT project_id, ticket_id, tag FROM tags WHERE project_id = ?`, one `SELECT from_id, to_id, kind, note FROM relations WHERE project_id = ?`; stitch tags/relations onto tickets in memory keyed by `id`. *Because* a project can have hundreds of tickets — the `get.ts` per-ticket N+1 pattern is the wrong shape for a full-project dump.
- **Select explicit columns, never `SELECT *`.** *Because* `relations` (and `tickets`) carry columns the renderer doesn't want (e.g. `relations.created_at`, confirmed in `001_init.sql`); name exactly the columns the record needs.
- **Ticket `id` is `TEXT` (e.g. `"T19"`), not an integer** — key the stitch maps by the string `id`; no numeric coercion. (Rules out the silent empty-tags class of bug.)
- **Tickets ordering by explicit priority rank**, matching Task 1: `ORDER BY (CASE priority WHEN 'P0' THEN 0 WHEN 'P1' THEN 1 WHEN 'P2' THEN 2 WHEN 'P3' THEN 3 WHEN NULL THEN 4 ELSE 5 END), id ASC` — but since the renderer re-groups by rank anyway, an in-memory sort is equally fine; whichever, no-priority and unknown values must land after `P3`, not first (a bare `ORDER BY priority` puts NULLs first in SQLite). The collector's order is a convenience; the renderer's rank is authoritative.
- **Relation grouping is NOT a shared export** — `get.ts`'s grouping (`get.ts:154-165`) lives inline in the private `fetchTicket()`. Copy that small outgoing/incoming-by-`kind` pattern into the collector and feed it the bulk relation rows; do **not** import from `get.ts` (there's nothing exported) and do **not** refactor `get.ts` for this ticket (scope). Note the duplication in a comment.
- Status counts computed via one `GROUP BY status` query, mirroring `stats.ts:55-66`.

**Don't:**
- Don't reuse `list.ts`'s default status filter or `LIMIT` — export is unfiltered and complete.
- Don't `import` a relation-grouping helper from `get.ts` — it isn't exported; copy the pattern.

**Implement:** Three bulk queries (explicit columns) + one status-count query + in-memory stitching keyed by string `id` + inline relation grouping.

**Verify:** `npm test src/lib/export-collect.test.ts` on a seeded in-memory DB:
- `it("returns every ticket regardless of status, no limit")`
- `it("attaches tags and grouped relations to each ticket")` — assert a ticket that has tags/relations comes back with `tags.length > 0` and a non-empty grouped `relations` (catches a silent stitch-key mismatch).
- `it("places no-priority and unknown-priority tickets after P3, not first")`
- `it("computes status counts")`

## Task 3a: `tickets.export` tool (unit-tested in a tmpdir)

**Files:**
- Create: `src/tools/export.ts`
- Create: `src/tools/export.test.ts`

**Decisions:**
- Tool name **`tickets.export`** (not overloading the reserved debug-only `tickets.dump`). Follows the `Tool<TArgs, TResult>` contract + `makeExportTool(db, getClientRoots)` factory.
- `ExportArgs = { project?: string; path?: string }`. Resolve project via `requireProject(db, { project: args.project }, getClientRoots)` (no `allowAll`). Since `allowAll` is false, `root_path` is always a real non-empty path (the `{ id: "all", root_path: "" }` sentinel cannot occur) — no empty-root guard needed.
- **Output path resolution:** `args.path` absolute → use verbatim; `args.path` relative → `path.resolve(project.root_path, args.path)`; omitted → `path.join(project.root_path, ".ai/TICKETS.md")`. `~` is **not** expanded (Node's `path` doesn't); document that in the tool description. Decided *because* it keeps the common case zero-config while allowing an explicit target.
- **Write:** `mkdirSync(path.dirname(target), { recursive: true })` then `writeFileSync(target, body, "utf-8")`. Body ends with a single trailing newline. I/O errors (`EACCES`, `ENOSPC`, …) propagate as thrown errors — the server envelope surfaces them; no special handling.
- **Tool description must state it OVERWRITES the target file** (drift defence + footgun honesty).
- **Return shape (compact, the point of the ticket):** `{ path: string, bytes: number, ticket_count: number, exported_at: string }`. Do **not** return the rendered body.
- `exported_at = nowIso()` computed **once** in `handle()`, passed into `renderExportMarkdown` and echoed in the result.

**Don't:**
- Don't write an `audit_log` row (export mutates no tickets).
- Don't return the markdown body in the result (defeats the compact-result purpose).
- Don't pass `allowAll` to `requireProject`.

**Implement:** `handle()` = resolve project → `collectProjectExport` → `renderExportMarkdown(exportedAt = nowIso())` → mkdir+write → return compact result.

**Verify:** `npm test src/tools/export.test.ts`. **Test hygiene:** build the project `root_path` under `fs.mkdtempSync(path.join(os.tmpdir(), "tg-export-"))`; `fs.rmSync(dir, { recursive: true, force: true })` in `afterEach`; **assert the resolved root is the tmpdir** (`expect(root).toContain(os.tmpdir())`) so a test can never clobber this repo's real `.ai/TICKETS.md`.
- `it("writes <root>/.ai/TICKETS.md and returns { path, bytes, ticket_count, exported_at }")`
- `it("the written file opens with the DO-NOT-EDIT comment and the timestamped banner")`
- `it("contains every ticket in the project grouped by priority")`
- `it("absolute path override writes verbatim to the given path")`
- `it("relative path override resolves under root_path, not cwd")`
- `it("re-exporting an unchanged DB changes only the banner timestamp line")` — export twice (two `nowIso()` values), split each file on `\n`, assert the only differing line is the banner blockquote.

## Caveats & known risks

- **Overwrite footgun (operational):** `tickets.export` overwrites the target path. In *this very repo* `.ai/TICKETS.md` is the rich hand-maintained file and this repo isn't registered in the DB — running the tool here would clobber it. That's intended behaviour for a real registered project, but call it out in the tool description ("overwrites the target file") and don't dogfood it against this repo's own hand-file. The banner makes a stale/wrong file self-identifying.
- **Default path == the migrate-once-then-delete file.** Writing `.ai/TICKETS.md` is exactly the user's requested target; just be aware it's the same filename the migration story deletes.
- **Relative `path` resolution** is against `project.root_path`, not `process.cwd()` — document so callers aren't surprised.
- **Numeric id ordering** (T10 vs T2) is intentionally *not* handled — string sort, consistent with `list.ts`. Future polish only.
