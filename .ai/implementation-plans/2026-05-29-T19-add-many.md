# T19 — `tickets.add_many` over a shared `insertBatch` core — Implementation Plan

> **For the implementer:** Use `subagent-driven-development` to implement task-by-task. TDD throughout (design spec §16). Every Acceptance bullet in ticket T19 maps to a named test.

**Goal:** Add a `tickets.add_many` MCP tool that creates many tickets (with auto-id, intra-batch parent/relation references, and one-transaction atomicity) over an `insertBatch` core extracted from `import_json`, returning a compact id list rather than full rows.
**Architecture:** Extract `import_json`'s 3-pass transaction into a reusable `insertBatch(db, opts)` in `src/lib/`. `import_json` and the new `add_many` become thin adapters: `import_json` = read file → validate → `insertBatch`; `add_many` = validate inline array → resolve auto-ids → `insertBatch`. A new `inferNextIds()` in `numbering.ts` assigns sequential ids across the batch.
**Tech Stack:** TypeScript ESM, better-sqlite3, MCP SDK, vitest.

---

## Ticket-scoped context

- **Why a new tool, not polymorphic `tickets.add`** (locked in T19): a single tool returning `{ ticket }` for one and `{ counts }` for many is a result-shape hazard for an LLM, and "delegate array to `import_json`" silently loses auto-id (`import_json` requires explicit `id`, `import-format.ts:70`). So `tickets.add` (`src/tools/add.ts`) is **untouched**.
- **Source of the shared logic:** `src/tools/import_json.ts:194-344` — the `doImport` transaction (3 passes: insert tickets + tags + `_created` audit; set `parent_id`; insert valid relations skipping dangling), plus the pre-transaction duplicate detection (`:129-145`), force-delete (`:199-206`), and post-transaction recount (`:331-344`).
- **Auto-id today:** `inferNextId(db, projectId)` returns ONE next id (`src/lib/numbering.ts:14`). Batch needs N sequential ids that also skip ids explicitly claimed within the same call.
- **Intra-batch reference limit (inherent, must document):** a ticket's `parent_id` or a relation endpoint can only reference a sibling that has an **explicit** id — you cannot reference an auto-id'd ticket because its id isn't known at call-authoring time. Same constraint already applies to `import_json` parent refs.
- **Atomicity:** `db.transaction(fn)` rolls back fully if `fn` throws (better-sqlite3). One invalid ticket ⇒ whole batch rolled back. This is intended (ticket: "single-add lets partial progress survive; batch does not").
- **Hard integration points found:** `tests/server.tools.test.ts:114` asserts `toHaveLength(21)` (→ 22) AND has 21 individual `toContain` lines (`:93-113`) — both the length AND a new `toContain("tickets.add_many")` must change. This file **spawns the built `dist/server.js`** (`:22,:33`), so it needs `npm run build` before it can pass when run alone. `README.md:71` Tool reference table needs an `add_many` row (after the `tickets.add` row, `:93`).
- **`insertBatch` returns a NEW type, not `ImportJsonResult`** (verified: `ImportJsonResult` at `import_json.ts:24-29` has no `created` field). Define `InsertBatchResult` = `{ imported?: boolean; dry_run?: boolean; created: string[]; counts: ImportCounts; warnings: string[] }`. `import_json.handle` adapts it to its own unchanged `ImportJsonResult` shape, **discarding `created`**.
- **No DB-level safety net for `status`/`type`/`priority`** (verified: `001_init.sql` has CHECK only on `effort`; `status TEXT NOT NULL` has none). `add_many`'s `parseArgs` is the *only* validator for these enums — a missed value would silently insert a bad row. Validate them explicitly.
- **Relation count is currently project-global** (verified: `import_json.ts:340` `SELECT COUNT(*) … WHERE project_id = ?` counts ALL project relations, not just inserted). Existing `import_json` tests import into empty DBs so total == inserted and don't catch it — but `add_many` on a non-empty project would over-report. Fix in `insertBatch`: count only newly-inserted relations (sum each `insertRelation.run().changes`; `INSERT OR IGNORE` returns `changes: 0` when deduped).
- **`closed_at` is NOT auto-set on insert** (verified: trigger is `AFTER UPDATE OF status`, `001_init.sql:101`). A ticket inserted with `status:'done'` keeps `closed_at = NULL`. This matches `tickets.add`'s existing behaviour — consistent, out of scope for T19.
- **`inferNextId` reads the DB on every call** (verified: `numbering.ts:15`). A loop of N `inferNextId` calls would return the SAME id N times (assigned ids aren't inserted yet). `inferNextIds` must do ONE scan and emit N ids in memory — it cannot be a wrapper around N calls.
- **Single-process atomicity:** better-sqlite3 is synchronous; the server is one Node process. There is no interleaving window between auto-id inference and the insert transaction **as long as no `await` sits between them**. See Task 3 `Don't`.
- **Enum sets are duplicated, not shared** (verified: `add.ts:10-12` and `import-format.ts:8-12` each define their own `VALID_*`; none are exported). `add_many` follows this existing pattern with its own local sets. Extracting a shared `enums.ts` is deliberately **out of scope** (would touch `add.ts` + `import-format.ts`; not what T19 asks) — recorded as won't-do in Caveats.

This *corrects* `import_json`'s count too; existing import_json tests use empty DBs (total == inserted) so they stay green.

- Don't change `import_json`'s `ImportJsonResult` shape or its `parseArgs` — only its `handle` body delegates inward. Its existing tests must stay green **unedited** (the new contract-guard test below is an *addition*, not a change to existing assertions).
- Don't let `created` reach `import_json`'s result — destructure it off in the adapter.
- Don't move `requireProject` / `readFileSync` / the `project_id !== projectId` check into `insertBatch` — those are adapter concerns; `add_many` resolves project differently (no file, no `project_id` field).
- Don't reintroduce per-row `nowIso()` drift — relations share one timestamp captured once inside the transaction (`import_json.ts:301`).

**Implement:** Move the duplicate-detection, dangling pre-scan, `dryRun` return, force/abort rule, `doImport` transaction (with precise relation-change counting), and recount out of `import_json.handle` into `insertBatch` returning `InsertBatchResult`; have `import_json.handle` call it with `{ projectId, tickets: parsed.tickets, relations: parsed.relations ?? Then add:

- `insert-batch.test.ts` covering the lib boundary directly: `created` lists inserted ids in input order; dup-without-force aborts; force overwrites; dangling relation skipped + warning string present; forward parent reference resolves; `_created` back-dated; a project with pre-existing relations → `counts.relations` equals only the newly-inserted count (locks the precise-count fix); `dryRun:true` → assert the **return shape** (`dry_run:true`, correct `counts`, `created: []`, `warnings`) AND DB unchanged (the shape assertion is primary; DB-emptiness is belt-and-suspenders since dryRun never opens the transaction).

## Task 2: `inferNextIds()` — sequential auto-ids across a batch

**Files:**
- Modify: `src/lib/numbering.ts` (add `inferNextIds`; keep `inferNextId` as-is, optionally re-expressed as `inferNextIds(db, p, 1, new Set())[0]` only if trivially safe — otherwise leave it untouched)
- Modify: `src/lib/numbering.test.ts` (add cases)

**Decisions:**
- Signature: `inferNextIds(db, projectId, count, reserved: Set<string>): string[]`. Returns exactly `count` ids using the same prefix/number rules as `inferNextId`.
- **Skip algorithm (explicit):** derive `(prefix, max)` from ONE DB scan; then `let n = max; const out = []; while (out.length < count) { n++; const id = prefix + n; if (!reserved.has(id)) out.push(id); }`. I.e. keep advancing the counter, emitting only ids not in `reserved`, until `count` non-reserved ids are collected — `count` is the number *emitted*, reserved skips don't consume it. This handles non-contiguous reserved sets (e.g. `{T5,T7}` from base T4, count 3 → `[T6,T8,T9]`).
- **Reuse the dominance logic, don't reimplement it.** `inferNextIds` and `inferNextId` must agree on prefix selection. Extract the shared `(prefix, max)` derivation (currently inline in `numbering.ts:24-67`, including the >50% dominance rule and the multiple-non-dominant-prefix→throw) into a private helper both call — OR have `inferNextIds` call `inferNextId` once to get the first id, parse off its `(prefix, startNum)` via `ID_PATTERN`, and step from there. Either way a project with a dominant prefix (e.g. `T`×3 + `BUG`×1) must succeed, not throw.
- Empty project (or no parseable ids): base is `T`, first id `T1`, then `T2`… (matches `inferNextId` empty→`T1`).
- `count` counts only the id-less tickets; existing DB ids above `max` don't exist, so only `reserved` drives skips.

**Don't:**
- Don't change `inferNextId`'s observable behaviour or signature — `add.ts:153` and its tests depend on it. If you extract a shared helper, `inferNextId` must keep returning the identical single id for every existing test.
- Don't let a dominant-prefix project throw — that would make `add_many` stricter than `add` on the same project.

**Implement:** Derive `(prefix, max)` once via the shared derivation; emit `count` ids by the skip-loop above.

**Verify:** Unit tests: empty project + count 3 → `[T1,T2,T3]`; populated `T1..T4` + count 2 → `[T5,T6]`; **`reserved={T5}`, base `T4`, count 2 → `[T6,T7]`** (the explicit-id-in-range case); **`reserved={T5,T7}`, base `T4`, count 3 → `[T6,T8,T9]`** (non-contiguous reserved); **dominant prefix (`T`×3 + `BUG`×1), count 2 → `[T5,T6]`, NOT a throw**; prefix `SETUP-` sole → `SETUP-<n+1>` sequence; multiple non-dominant prefixes → throws. Plus the JSDoc states the skip-loop contract.

## Task 3b: `tickets.add_many` — `handle` (auto-id + insertBatch)

**Files:**
- Modify: `src/tools/add_many.ts` (replace the stubbed `handle`)
- Modify: `src/tools/add_many.test.ts` (handle/runtime cases)

**Decisions:**
- `handle`: `await requireProject(...)` → split tickets into explicit-id vs id-less, build `reserved` = set of explicit ids → `inferNextIds(db, projectId, idless.length, reserved)` → assign auto-ids back to the id-less tickets **in input order** → apply per-ticket defaults (status→open, type→task, description→"", created_by→claude) so every ticket is a fully-resolved `ImportTicket` → `insertBatch({ projectId, tickets, relations })` → return `{ created, count, warnings? }`.
- **Auto-id assignment runs synchronously with the `insertBatch` call** — `inferNextIds` and `insertBatch` are both synchronous better-sqlite3 work; place them with **no `await` between them** (the only `await` is `requireProject`, before inference). See Don't.
- **`parent_id` resolution:** an explicit-id sibling referenced as `parent_id` resolves via `insertBatch`'s existing Pass 2 (insert all with `parent_id=NULL`, then UPDATE). An **auto-id'd** ticket cannot be a `parent_id` target (its id is unknown to the caller at author time) — this is an inherent limit, documented in the tool `description`, not a code path. A `parent_id` pointing at neither a batch ticket nor an existing DB ticket surfaces as the FK error `insertBatch` already raises.
- **Result shape (compact):** `{ created: string[]; count: number; warnings?: string[] }`. `count = created.length`. Omit `warnings` when empty.
- Tool `description` must state: batch create; returns ids not rows; **all-or-nothing** (one invalid ticket rolls back the whole batch); auto-id'd tickets cannot be referenced as `parent_id`/relation endpoints within the same call — give referenced tickets explicit ids.

**Don't:**
- Don't return full ticket rows — the compact id list is the entire point (T20 alignment).
- Don't place any `await` between `inferNextIds(...)` and `insertBatch(...)` — that would open an interleaving window where a concurrent call could claim the same ids. Synchronous back-to-back execution is the atomicity guarantee in a single-process server.
- Don't duplicate insert/transaction logic — `add_many` must go through `insertBatch`.

**Implement:** Resolve project, assign sequential auto-ids (skipping explicit ids) to id-less tickets, normalise defaults, delegate to `insertBatch`, return the compact result.

**Verify:** TDD, one test per ticket Acceptance bullet:
- N inline tickets → all created in one call, `created` lists their ids in input order, result has **no `ticket`/full-row** field.
- All `id` omitted on a `T1..T4` project → `created == [T5,T6,…]`.
- Mixed explicit + auto ids in one call → no collision (auto skips the explicit id); assert the explicit id is untouched and autos fill the gaps.
- A ticket with `parent_id` pointing at an **explicit-id** sibling in the same call → parent resolves (multi-pass), assert the child's stored `parent_id`.
- One ticket with an invalid field that reaches the DB (or a `parent_id` to a nonexistent ticket) → whole batch rolls back (project ticket count unchanged) and a clear `McpError` naming the offending ticket.
- Tags normalised + deduped; one `_created` audit row per ticket; `warnings` omitted when empty.

## Caveats & known risks

- **`inferNextId` refactor risk:** safest to share a `(prefix, max)` helper and leave `inferNextId`'s output identical. Don't trade a clean tool for a regression in the well-tested single-add path.
- **`created` field leaking into `import_json`:** the adapter must destructure `created` off; `import_json`'s `ImportJsonResult` is a shipped contract (T20 owns response-shape changes). Guarded by the additive `not.toHaveProperty("created")` test in Task 1.
- **Relation `now` timestamp:** preserve the single in-transaction `nowIso()` for all relations; don't reintroduce per-row clock reads.
- **Auto-id + reference interaction:** documented as a caller constraint, not a code path. Temp-handle references (e.g. `$1`) would be new scope — out of T19.
- **Won't-do — shared `enums.ts`:** the challenger flagged that `VALID_*` sets live in three places (`add.ts`, `import-format.ts`, and now `add_many.ts`). Extracting a shared module would touch two well-tested existing files for no behaviour change — out of T19's scope. Recorded here so a future cleanup ticket can pick it up.
- **Won't-do — `closed_at` on insert-as-done:** a ticket created with `status:'done'` keeps `closed_at = NULL` (trigger is `AFTER UPDATE OF status` only). This matches `tickets.add` — fixing it would be a separate ticket affecting both tools.

### Technical Context & Learnings
- **`insertBatch` is the shared insert core.** `import_json` (file → validate → `insertBatch`) and `tickets.add_many` (inline array → resolve auto-ids → `insertBatch`) are thin adapters. `insertBatch` returns `InsertBatchResult` (with `created: string[]`); `import_json` destructures `created` off to preserve its `ImportJsonResult` contract.
- **Relation count semantics changed (intentionally):** `insertBatch` now reports *newly-inserted* relations (summed `INSERT OR IGNORE … .changes`), not project-global `COUNT(*)`. Benign for `import_json`'s existing tests (they import into empty DBs). The `dryRun` path still reports the pre-scan `validRelationCount`/raw `tagCount` — hence Finding 1.
- **Batch auto-id:** `inferNextIds(db, projectId, count, reserved)` does ONE DB scan via a shared `deriveBase` helper (so `inferNextId` stays behaviourally identical) then emits `count` ids skipping `reserved` (the explicit ids in the same batch) — auto and explicit ids never collide.
- **Atomicity invariant:** in `add_many.handle` there is NO `await` between `inferNextIds` and `insertBatch` (the only `await` is `requireProject`, before inference). In a single-process synchronous-better-sqlite3 server this closes the only window in which a concurrent call could claim the same ids. A load-bearing comment marks it — do not insert an `await` there.
- **`parent_id` validated upfront in `add_many` (not in `parseArgs`):** auto-ids aren't known at parse time, so `handle` validates each resolved ticket's `parent_id` against {batch ids ∪ existing DB ids} with a synchronous scan, throwing a clean `McpError` (mirrors `tickets.add`). This replaced a raw `SqliteError` FK leak from `insertBatch` Pass 2 (caught in review) and also enforces the documented limit that auto-id'd tickets can't be referenced within the same call.
- **Self-parent edge:** a ticket whose `parent_id` equals its own id passes validation (it's in the batch) — consistent with `tickets.add`, which has no creation-time cycle detection. Not an integrity problem (depth-guarded readers tolerate cycles). Accepted.
