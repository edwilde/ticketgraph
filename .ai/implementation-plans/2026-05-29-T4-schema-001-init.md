## Ticket-scoped context

- **The design spec §5 is authoritative.** This ticket implements it verbatim — column names, types, constraints, FKs, indexes, triggers, and the audit-row shapes. The plan does NOT restate the SQL; the implementer pulls it from the spec.
- **FK strangeness:** `(project_id, id)` is the PK on `tickets`. The self-FK for `parent_id` is therefore `(project_id, parent_id) REFERENCES tickets(project_id, id)`. SQLite supports composite foreign keys via `FOREIGN KEY (a, b) REFERENCES t(x, y)`. The `relations` table has two composite FKs (one to `from`, one to `to`). `audit_log` has NO foreign key by design (spec §5: decoupled to survive future hard-deletes and re-imports).
- **`PRAGMA user_version` is currently 1 on any DB created during T3** (T3 ran the empty 001_init.sql). T4 fills the same file. **Stale DBs created during T3 are NOT auto-upgraded** — they won't re-apply 001. This is acceptable for pre-MVP because no production data exists yet. Anyone with a stale dev DB at `~/.claude/tickets.db` must `rm` it. Document in caveats; do NOT add a 002 just to dodge this — keeps history clean for the imminent first migration.
- **FTS5 sync triggers** are critical: any test/use that updates `tickets.title` or `tickets.description` and then queries `tickets_fts` will fail if the trigger is missing or wrong. Spec §5 has the three triggers (ai/ad/au) verbatim.
- **`tickets_fts_au` only triggers on UPDATE OF title, description.** Other column updates (status, priority, etc.) do not touch FTS. This is correct; FTS only indexes those two columns.
- **`closed_at` triggers**: spec §5 lists `tickets_closed_at_set` (transition into done/deferred → set if NULL) and `tickets_closed_at_clear` (transition out → clear). Audit-log rows for the status change are written by application code, NOT a trigger. T4 only ships the closed_at triggers.
- **Index list (spec §5):** `idx_tickets_status`, `idx_tickets_priority`, `idx_tickets_epic`, `idx_tickets_type`, `idx_tickets_parent`, `idx_relations_to`, `idx_relations_from`, `idx_tags_tag`, `idx_audit_changed_at`, `idx_audit_ticket`. Don't skip any — they back the §10 latency budgets.
- **No `CHECK (status IN ...)` constraint.** Spec §5 leaves status validation to application code (consistent with the `kind` validation choice for relations). Don't add a CHECK.
- **`effort` CHECK constraint** IS in the spec: `effort INTEGER CHECK (effort IS NULL OR effort IN (1, 2, 3, 5, 8, 13))`. Include it.
- **Tags are stored lowercase, trimmed** — but normalisation is application-level (spec §5). The schema itself has no constraint.
- **Reserved project ids (`all`, `current`)** are rejected by application code in T5's `register_project`. The schema permits them.

## Caveats & known risks

- **Stale T3-era dev DBs:** if anyone ran the server between T3 and T4 and persisted a DB at `~/.claude/tickets.db`, that DB has `user_version=1` and an empty schema. T4's filled migration won't re-run. Workaround: `rm ~/.claude/tickets.db` once. Acceptable pre-MVP; document in README later if it bites.
- **FTS5 availability:** `better-sqlite3@11` ships SQLite with FTS5 enabled. If a future native upgrade drops FTS5, the migration will throw at `CREATE VIRTUAL TABLE tickets_fts USING fts5(...)`. Detected immediately on first startup.
- **Trigger interaction:** SQLite fires triggers in declaration order; `tickets_fts_au` only watches `OF title, description`, so unrelated `tickets.status` updates do NOT touch FTS. That's correct, but worth knowing if FTS ever indexes a third column.
- **Compound FK to self:** `(project_id, parent_id) REFERENCES tickets(project_id, id)` requires the referenced columns to be a PRIMARY KEY or UNIQUE — `(project_id, id)` is the PK, so this works.
- **Audit log table has no FK:** intentionally decoupled per spec §5. Tests should not expect cascade behaviour on audit_log rows.
- **`tickets.parent_id` `ON DELETE SET NULL`:** when an umbrella parent is deleted, children become orphans (parent_id=NULL), not cascade-deleted. T8's `tickets.validate` will surface orphans if any survive.

### Technical Context & Learnings
- **FTS5 shadow tables**: every `CREATE VIRTUAL TABLE … USING fts5(...)` produces 5+ shadow tables (`_config`, `_content`, `_data`, `_docsize`, `_idx`) in `sqlite_master`. Tests that introspect schema must filter or use inclusion checks.
- **SQLite auto-indexes**: every PRIMARY KEY and UNIQUE constraint generates an internal `sqlite_autoindex_<table>_N` entry. Authored indexes coexist with these; introspection tests should account for both kinds.
- **`closed_at` trigger does NOT fire on INSERT**: only `UPDATE OF status`. Inserting a row with `status='done'` leaves `closed_at` NULL unless explicitly set. This is by design (spec §5).
- **Composite self-FK works**: `(project_id, parent_id) REFERENCES tickets(project_id, id)` is valid SQLite syntax because `(project_id, id)` is the PK.
- **Stale T3-era dev DBs** (with `user_version=1` and empty schema) will NOT pick up T4's filled schema. Workaround: delete and re-create. Acceptable pre-MVP.
