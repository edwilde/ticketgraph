# T6 — `tickets.search` with FTS5

> **For the implementer:** Use `subagent-driven-development` to implement task-by-task.

**Goal:** Ship `tickets.search` — a BM25-ranked full-text search over `tickets_fts` with title weighted 3× over description, snippets, default status filtering, and a <1000-token response budget.
**Architecture:** One new `Tool<TArgs, TResult>` factory (`makeSearchTool(db)`). A small `src/lib/fts.ts` sanitises the user query into safe FTS5 MATCH syntax (the single most important correctness concern). Joins `tickets_fts` → `tickets` to layer structured filters on top of the FTS match. Register in `makeToolRegistry`.
**Tech Stack:** TypeScript ESM, better-sqlite3 (FTS5 + bm25 + snippet built in). No new deps.

---

## Ticket-scoped context

- **FTS5 column indices** for `tickets_fts(project_id UNINDEXED, ticket_id UNINDEXED, title, description)`: project_id=0, ticket_id=1, **title=2, description=3**. `bm25(tickets_fts, 3.0, 1.0)` weights columns positionally — the two weights map to the two *indexed* columns (title, description) in order, so 3.0 = title, 1.0 = description. `snippet(tickets_fts, 3, ...)` snippets the **description** column (index 3), per spec §8.
- **bm25 sign convention**: SQLite's `bm25()` returns a value where **more negative = better match**. `ORDER BY bm25(...) ASC` yields best-first. Return the raw bm25 as `score` and document "lower is better" in the tool description. Ties broken by `id ASC` (spec §8).
- **FTS query sanitisation is the load-bearing correctness concern.** A raw user query like `foo:bar` or `wes(` is valid English but invalid FTS5 MATCH syntax and throws `SQLITE_ERROR: fts5: syntax error`. The sanitiser must turn arbitrary text into a safe MATCH expression. Approach: split on whitespace; for each token, double any embedded `"` then wrap the token in double quotes (FTS5 treats a quoted string as a literal term/phrase); join tokens with a space (FTS5 implicit AND). Quoted single barewords STILL stem under `porter`, so `"estimators"` matches "estimator". Empty-after-sanitise → `McpError(InvalidParams, "search query is empty")`.
- **`snippet()` token-count arg** (last arg, default 16) is what `snippet_length` adjusts — NOT a character count. Spec §8 says "~240 chars"; that's the *effect* of ~16 tokens. `snippet_length` overrides the 16. Clamp to a sane range (1–64) to avoid abuse.
- **Default filters** (spec §6): `status IN ('open','in_progress','blocked')`, `include_done: false`, default `limit = 10`. `include_done: true` removes the status default (includes done/deferred). Explicit `status` filter overrides the default.
- **Return shape** (spec §6): array of `{ id, title, status, priority, type, snippet, score }`. Wrap as `{ project, count, hits: [...] }` for consistency with `tickets.list`'s `{ project, count, rows }`.
- **Token budget** (spec §10): <1000 tokens. 10 hits × (240-char snippet + small meta) ≈ well under 4000 bytes. Assert `bytes < 1000 * 4`.
- **Latency budget** (spec §10): <50ms p99 against a 1000-row fixture. FTS5 + bm25 is fast; the JOIN to `tickets` is indexed by PK. Assert a generous bound to avoid CI flakiness (see Task 4 note).
- **Project scope**: `requireProject(db, { project }, process.cwd(), allowAll: true)` — search supports `project: "all"` (cross-project) per spec §6's read-tool convention; when `all`, drop the `project_id` predicate.
- **No prefix/fuzzy/trigram** (spec §8): porter+unicode61 only. Don't add `*` prefix matching unless a token already carries it — and the sanitiser quotes tokens, so prefix syntax is neutralised by design. That's correct for v1.

## Task 1: `src/lib/fts.ts` — query sanitiser

**Files:**
- Create: `src/lib/fts.ts` + `src/lib/fts.test.ts`

**Decisions:**
- Export `sanitiseFtsQuery(q: string): string`.
- Algorithm:
  1. `q.trim()`. If empty → return `""` (caller throws InvalidParams).
  2. Split on `/\s+/`.
  3. For each token: strip nothing, but escape embedded `"` by doubling (`"` → `""`), then wrap the whole token in `"..."`.
  4. Join with a single space.
- Result example: `foo bar` → `"foo" "bar"`; `wes(` → `"wes("`; `a "b` → `"a" """b"` (the lone `"` is doubled then wrapped — valid FTS5).
- This guarantees no FTS5 operator (`:`, `*`, `(`, `OR`, `NEAR`, `-`) is interpreted; everything is a literal AND-ed term. Stemming still applies.

**Don't:**
- Don't try to preserve FTS5 operators — a single-user search box wants literal terms, not query-language passthrough (spec §8: no fuzzy/advanced).
- Don't lowercase — `unicode61` tokeniser is case-insensitive already.
- Don't strip punctuation inside tokens — quoting makes it safe; the tokeniser handles word-splitting.

**Implement:** The sanitiser + unit tests.

**Verify:** Unit tests:
- `"foo bar"` → `"foo" "bar"`.
- single term → quoted single term.
- embedded quote doubled.
- FTS-operator characters (`:`, `(`, `*`, `-`) survive as literals (assert the output, and ideally run a real MATCH against a temp DB to prove no syntax error).
- empty / whitespace-only → `""`.

## Task 2: `tickets.search`

**Files:**
- Create: `src/tools/search.ts` + `src/tools/search.test.ts`

**Decisions:**
- Factory `makeSearchTool(db)`.
- Args: `{ project?, q: string, status?, priority?, type?, epic?, include_done?, limit?, snippet_length? }`.
  - parseArgs: `q` required non-empty string; `status` string|string[]; `priority`/`type`/`epic` optional strings; `include_done` optional boolean (default false); `limit` optional int (default 10, clamp 1–50); `snippet_length` optional int (default 16, clamp 1–64).
- handle:
  1. `requireProject(..., { allowAll: true })`.
  2. `const matchExpr = sanitiseFtsQuery(args.q)`; if empty → `McpError(InvalidParams, "search query is empty")`.
  3. Build SQL:
     ```sql
     SELECT t.id, t.title, t.status, t.priority, t.type,
            snippet(tickets_fts, 3, '<mark>', '</mark>', '…', ?) AS snippet,
            bm25(tickets_fts, 3.0, 1.0) AS score
     FROM tickets_fts
     JOIN tickets t ON t.project_id = tickets_fts.project_id AND t.id = tickets_fts.ticket_id
     WHERE tickets_fts MATCH ?
       [AND t.project_id = ?]            -- unless project: "all"
       [AND t.status IN (...)]           -- default or explicit; skipped if include_done && no explicit status
       [AND t.priority = ?] [AND t.type = ?] [AND t.epic = ?]
     ORDER BY bm25(tickets_fts, 3.0, 1.0) ASC, t.id ASC
     LIMIT ?
     ```
     All values parameterised. `snippet_length` is the first bound param (the `?` in snippet()).
  4. Status filter logic: if explicit `status` given → use it. Else if `include_done` → no status filter. Else → default `('open','in_progress','blocked')`.
  5. Return `{ project: <id|"all">, count: hits.length, hits }`.

**Don't:**
- Don't string-interpolate the query or any filter into SQL — `MATCH ?` takes the sanitised expression as a bound param; FTS5 accepts a bound-parameter match string.
- Don't return descriptions in full — the snippet is the only body text returned (budget).
- Don't sort by anything but bm25 then id (spec §8).
- Don't apply `created_after`/`parent_id`/`tag` filters — those are `tickets.list`'s job; search's filter set is narrower (spec §6).

**Implement:** Tool with sanitiser + dynamic-but-parameterised SQL.

**Verify:** Unit tests in Task 3.

## Caveats & known risks

- **FTS5 MATCH with a bound parameter**: `WHERE tickets_fts MATCH ?` works — FTS5 accepts the match expression as a bound string. Do NOT inline the sanitised query into the SQL text; bind it.
- **bm25 weights are positional over INDEXED columns only**: `bm25(tickets_fts, 3.0, 1.0)` → 3.0 applies to `title`, 1.0 to `description` (the UNINDEXED columns don't count). If a future column is added to the FTS table, these weights shift — keep them in sync with the schema.
- **Snippet column index is 3 (description)**: snippeting the title (index 2) would be near-useless (titles are short). Spec §8 pins description.
- **Sanitiser trade-off**: quoting every token disables FTS5's query language (no user-facing `OR`, `NEAR`, prefix `*`). That's intentional for a single-user search box (spec §8: no advanced/fuzzy). If power-query is ever wanted, add an opt-in `raw: true` that bypasses the sanitiser — out of scope for T6.
- **Latency test flakiness**: the 50ms p99 in spec §10 is a design target measured on the author's machine, not a CI assertion. The test uses a generous bound to catch real regressions.
- **Empty FTS table**: searching a project with zero tickets returns `{ count: 0, hits: [] }`, not an error.

### Technical Context & Learnings
- **bm25 weight positional gotcha (load-bearing)**: SQLite's `bm25(fts, w0, w1, ...)` takes ONE weight per table column, *including UNINDEXED columns*, in declaration order. For `fts5(project_id UNINDEXED, ticket_id UNINDEXED, title, description)` you MUST pass four weights — `bm25(fts, 1.0, 1.0, 3.0, 1.0)` — to weight title 3×. Passing only two weights silently assigns them to the unindexed columns (which carry no tokens) and leaves the real columns at the default 1.0. This is an easy, invisible bug: results still come back ranked (BM25 naturally favours short fields), just not with the intended weighting. **Any future FTS column change must re-check these weights.**
- **Test the mechanism, not the symptom**: a ranking test that passes because of an incidental property (short title fields) is a false sense of security. The regression guard now isolates the weight by equalising field lengths.
- **FTS query sanitisation**: `sanitiseFtsQuery` quotes every whitespace-delimited token (doubling embedded `"`), neutralising all FTS5 operators. Quoted single barewords still stem under porter. Empty → tool throws InvalidParams.
- **bm25 sign**: more negative = better; `ORDER BY bm25(...) ASC, t.id ASC`. `score` returned raw (lower is better), documented in the tool description.
